# API Contract

This document is the source of truth for the public API. Changes to field names,
response envelopes, status codes, or validation rules require an explicit contract
revision before implementation.

All request and response bodies use `application/json`. Timestamps use RFC 3339
with an explicit timezone. Unknown request fields are rejected.

## `POST /sensor-data`

Stores one greenhouse sensor reading.

### Request

```json
{
  "device_id": "sensor-001",
  "temperature": 28.5,
  "humidity": 71.2,
  "timestamp": "2026-09-19T10:30:00Z"
}
```

Validation rules:

- `device_id`: required, non-empty string, maximum 100 characters; allowed
  characters are letters, numbers, `.`, `_`, and `-`.
- `temperature`: required finite number. No arbitrary domain range is imposed.
- `humidity`: required finite number from `0` through `100`, inclusive.
- `timestamp`: required timezone-aware RFC 3339 timestamp.

### Success response

Status: `201 Created`

```json
{
  "success": true,
  "message": "Sensor data stored successfully",
  "data": {
    "id": 1
  }
}
```

## `POST /device-control`

Publishes a control command to `greenhouse/control/{device_id}`. A successful
response confirms QoS 1 acknowledgement from the broker, not execution by the
physical device.

### Request

```json
{
  "device_id": "fan-001",
  "command": "ON"
}
```

Validation rules:

- `device_id`: required, non-empty string, maximum 100 characters; allowed
  characters are letters, numbers, `.`, `_`, and `-`.
- `command`: required, case-sensitive enum with the values `ON` and `OFF`.

The backend publishes this structured MQTT payload. `timestamp` is generated by
the backend at publish time:

```json
{
  "device_id": "fan-001",
  "command": "ON",
  "timestamp": "2026-09-19T10:35:00Z"
}
```

### Success response

Status: `200 OK`

```json
{
  "success": true,
  "message": "Device control command published successfully",
  "data": {
    "device_id": "fan-001",
    "command": "ON"
  }
}
```

## `GET /status`

Reports backend and dependency health. The endpoint returns `200 OK` while the
backend can produce a health report, including when a dependency is unavailable.

### Healthy response

```json
{
  "status": "healthy",
  "services": {
    "backend": "up",
    "database": "connected",
    "mqtt": "connected"
  }
}
```

When either dependency is unavailable, `status` is `degraded` and that service is
`disconnected`. `backend` is `up` whenever this response can be returned.

## Error response

Validation failures use `422 Unprocessable Content`. Database or MQTT dependency
failures use `503 Service Unavailable`. Every API error uses this envelope:

```json
{
  "success": false,
  "error": {
    "code": "MQTT_UNAVAILABLE",
    "message": "MQTT broker is unavailable"
  }
}
```

Validation failures use `VALIDATION_ERROR` and add field-level `details` inside
the `error` object. Internal exceptions and credentials are never included in a
response. Stable error codes currently include:

- `VALIDATION_ERROR`
- `DATABASE_UNAVAILABLE`
- `MQTT_UNAVAILABLE`
- `HTTP_ERROR`
- `INTERNAL_SERVER_ERROR`
